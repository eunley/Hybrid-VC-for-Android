# Hybrid VC for Android

一款面向 Android 的免费变声器，支持文件转换、实时变声、快捷录音和本地 HTTP 接口。

项目参考了 [ultimate-rvc-mobile](https://github.com/Sharl210/ultimate-rvc-mobile) 的模型使用方案，并针对手机端进行了优化与加速。当前采用通用 HuBERT、RMVPE 与 SVC 的 enc/dec 模型组合，音色模型主要兼容 **so-vits-svc 4.0** 生态，可从社区获取后导入使用。

这是一个个人探索项目，主要代码由 **GPT、DeepSeek 辅助编写**，由本人测试和调整。我的开发经验和测试设备都有限，也欢迎有兴趣的开发者参与改进和fork。个人认为项目本身已经较为完善，没有必要再添加新的功能，但如果你提出了好的建议，我也可能会采纳和改进

## 功能特色

### 导入角色，无需电脑转换

导入兼容的 so-vits-svc 4.0 角色后，应用会在手机上将权重转换为可运行的 ONNX 模型，无需先用电脑转换。使用 NPU 时，还需要完成对应的设备端编译。

应用不负责训练音色模型。如果社区中没有你需要的角色，仍可能需要使用电脑自行训练。

### 面向手机端的推理优化

在 **骁龙 8 Elite Gen 5（SM8850）** 设备上，以 **3000 ms 分片**测试时，曾测得：

| 推理方式 | RTF（约） |
| --- | ---: |
| CPU | 0.65 |
| NPU | 0.20 |

RTF 是处理耗时与音频时长的比值，数值越低表示处理越快。例如，RTF 为 0.20 表示处理 10 秒音频约需 2 秒。它不等于实时模式的端到端延迟。

以上为个人设备上的测试结果，并非所有机型的性能保证。实际速度会受到模型、分片大小、温度、后台负载和加速后端等因素影响。

### 实时变声与快捷录音

- **Root 模式**：支持直接采集、变声和音频注入，无需安装额外的挂载模块。实际可用性取决于系统及目标应用。
- **免 Root 模式**：支持快捷录音、转换和播放；不等同于向其他应用直接注入麦克风音频。
- 支持文件变声与批量处理，适合离线转换。

### 本地 HTTP 服务

启用 HTTP 服务后，可通过脚本、其他设备或具备 HTTP 工具能力的 AI 客户端调用接口，进行角色管理、上传和音频转换。角色 ZIP 支持分片上传、断点续传与 SHA-256 校验。

- 默认关闭服务，并默认仅允许本机访问。
- 关闭“仅本机访问”后，可供局域网设备访问。
- 支持自定义访问令牌或随机生成密钥。**令牌留空时不验证请求**；设置后，每个请求须携带 `Authorization: Bearer <token>`。
- HTTP 本身不加密，请在可信网络使用。

接口说明见 [local-http-api.txt](assets/local-http-api.txt)，角色上传客户端见 [upload_role.py](assets/upload_role.py)。AI 搜索角色需要客户端自行具备联网能力，导入的模型也需要符合应用支持的格式。

## 使用与兼容性

当前构建主要测试设备为realmeGT8pro(RMX5200，安卓16版本，骁龙 8 Elite Gen 5（SM8850），其他设备的适配和性能尚未充分验证。

基本使用流程：

1. 安装应用，完成所需权限。
2. 导入兼容的 so-vits-svc 4.0 角色，等待转换完成。
3. 选择角色和推理后端；使用 NPU 时需要完成设备端编译，使用CPU时则无需编译。
4. 加载模型后，进行文件转换、实时变声或快捷录音。

完整版 APK 包含 HuBERT、RMVPE 等基础模型，因此体积较大。源码仓库不包含这些外置模型和依赖运行库；自行构建请参阅 [BUILDING.md](BUILDING.md)。

## 常见问题

### 为什么其他设备上的兼容性不如测试机型？

目前主要围绕本人持有的 SM8850 设备开发和测试，没有足够的设备覆盖不同芯片、系统和厂商实现。尤其是 NPU 后端，能否运行还取决于硬件和运行库兼容性。

如果遇到问题，欢迎提供设备型号、Android 版本、应用版本、使用的后端和复现步骤。分享日志前请先移除令牌及个人信息。

### 为什么高负载时表现会变差？

手机的算力、内存带宽和散热能力有限。后台任务争抢资源、发热降频或处理速度跟不上输入，都可能影响实时处理的流畅度和稳定性。

### 为什么转换质量有时不理想？

转换效果取决于角色模型、输入音频质量、音高设置以及当前采用的推理方案。背景音乐、混响、环境噪声和多人说话都可能带来杂音或失真，建议优先使用清晰、单人的干声。

目前没有找到同时兼顾手机端速度、功耗和质量的更好方案。额外加入人声分离会进一步增加计算量，因此尚未集成完整的干声提取流程。当前方案也不能保证与桌面端完整 SVC/RVC 流程具有相同的效果。

有兴趣的用户可以在 Termux 中自行探索其他 SVC/RVC 实现，但这不属于本应用当前提供的功能。

### 为什么采用混合模型方案？

这是早期 AI 辅助开发时采用的方案。后续测试中，它在现有设备上取得了相对可接受的速度，因此沿用了下来。这是当前实现的取舍，不代表它是所有设备和场景下的最优方案。

### 为什么没有提供 GPU 加速？

开发过程中尝试过 GPU 路线，但在当前测试设备和配置下，收益不如 NPU，因此没有作为主要加速方案提供。这并不代表 GPU 在所有设备上都没有价值。

### 还会频繁更新吗？

目前主要功能已接近预期，后续可能只进行少量修复，也可能长期不再更新。作为个人项目，暂不承诺更新频率或持续维护周期。

### 开启降噪后变声失效？
因为降噪是轻量模型，可能导致把人声也给降噪导致的，关闭降噪再试试

## 技术栈

| 层级 | 技术与用途 |
| --- | --- |
| 应用主体 | Java，基于 Android 原生 Activity、Service 和 View 构建界面与后台任务 |
| 界面与视觉 | Android Canvas、自定义 View；Android 13 及以上使用 RuntimeShader / AGSL 实现部分玻璃、折射效果 |
| 多语言 | Android 字符串资源及应用内 Locale 切换 |
| 模型推理 | ONNX Runtime Java/JNI，CPU 推理及 Qualcomm QNN / HTP（NPU）后端 |
| 音频模型 | HuBERT 语音特征提取、RMVPE 音高提取，以及 SVC enc/dec 角色模型 |
| 角色导入 | Java 实现权重读取、映射与 ONNX 模型生成，设备端准备 NPU 所需编译产物 |
| 音频处理 | Android 音频解码接口、AudioRecord / AudioTrack、分片调度与交叉淡化 |
| 原生组件 | C / JNI、RNNoise 降噪，以及 Root 音频采集与注入辅助逻辑 |
| HTTP 接口 | Java Socket 实现的轻量 HTTP 服务，Bearer Token 验证及可恢复的分片上传 |
| 脚本与测试 | Python 上传客户端，Java / Python 接口与协议测试 |
| 构建工具 | Termux、Shell、OpenJDK、Clang、aapt、D8/R8、zipalign、apksigner；当前未使用 Gradle |

具体构建依赖、外部模型要求及操作步骤见 [构建说明](BUILDING.md)。

音频处理设置：降噪将干净信号送入变声，再回混原始减干净信号的残差以保留背景，不使用静音门。独立音量限制默认关闭，将约20毫秒输出 RMS 限制到对应原始输入以内，峰值不超过1。文件、批量和快捷录音共用文件设置，实时设置在启动时固定；HTTP 使用严格布尔字段 `denoise` 和 `volumeLimit`，均默认 false。任一选项开启时不做最终全段峰值归一化；均关闭时保留旧的0.95峰值归一化。

音量比较基于处理链解码后的单声道 16 kHz 输入，经对齐重采样后与 44.1 kHz 输出比较。残差回混并非严格的人声/伴奏分离，可能保留部分原声，也会保留被降噪移除的噪声。音量限制采用固定对齐的 20 ms RMS 窗口，不是逐采样或任意滑动窗口的分贝保证。
